# وضعیت راستی‌آزمایی دسترسی بازار V2 — ۱۴۰۵/۰۷/۱۵

این گزارش مربوط به checkout محلی است؛ هیچ تستی روی دیتابیس production اجرا نشده و `MARKET_ACCESS_V2_ENABLED` همچنان به‌صورت پیش‌فرض `False` است.

## نتیجهٔ محلی

- مجموعهٔ هدفمند V2 و بخش‌های وابسته: ۱۷۶ تست، همگی موفق.
- رگرسیون نهاییِ مسیرهای Basic، لایو، سیگنال VIP و اعلان: ۶۰ تست، همگی موفق.
- کل suite روی دیتابیس‌های موقت SQLite و با چهار worker، پس از همهٔ تغییرات این نوبت: ۵۸۰ تست، موفق؛ ۲ تست skip.
- `manage.py check`: بدون ایراد؛ `makemigrations --check --dry-run`: بدون drift.
- `manage.py spectacular --validate`: خروج با کد صفر، بدون error؛ ۸ warning مربوط به نام‌گذاری enumهای مشترک باقی مانده است.
- مهاجرت‌های `accounts.0022` تا `0024` در دیتابیس موقت تست ساخته و اعمال شدند؛ روی staging/production اعمال نشده‌اند.

سقف ۲ مگابایتی برای پاسخ JSON providerهای بازار و نمودار افزوده شد؛ پاسخ بیش‌ازحد بزرگ دوباره دانلود نمی‌شود. ۳۹ تست بازار و قرارداد V2 جداگانه و سپس suite کامل ۵۸۰تایی روی نسخهٔ نهایی موفق شدند. `GET/PATCH /api/accounts/profile/details/` اکنون مانند dashboard وضعیت `market_access_v2` را برمی‌گرداند؛ ۳۳ تست مرتبط با profile و V2 جداگانه موفق شدند.

## اصلاح رگرسیون‌های قدیمی

۱۰ failure اجرای قبلی از تست‌هایی بودند که payload ثبت‌نام، سطح مؤثر Level 2، مسیر سیگنال legacy یا قرارداد cache و پاسخ بدون provider را مطابق نسخهٔ فعلی تنظیم نکرده بودند. این تست‌ها بدون تغییر رفتار runtime به‌روزرسانی شدند؛ ابتدا هر ۱۰ تست به‌صورت جداگانه و سپس کل suite موفق شد. برای بازار، snapshot تازهٔ دیتابیس عمداً پاسخ fresh می‌دهد و فقط snapshot قدیمی با شکست provider باید stale باشد. API quote نیز در نبود دادهٔ واقعی طبق قرارداد موجود `200` با `available=false` و `results=[]` می‌دهد، نه قیمت ساختگی.

## شرط عبور به staging

راهنمای عملی staging، ترتیب بک‌آپ/مقایسه/توقف و مرز rollback در [market-access-v2-staging-runbook-fa.md](market-access-v2-staging-runbook-fa.md) ثبت شده است. دستور فقط‌خواندنی `audit_market_access_v2` برای شمارش‌های تجمیعی قبل/بعد از migration اضافه شد؛ دو تست آن و سپس suite کامل ۵۸۰تایی موفق شدند.

1. بک‌آپ بازیابی‌پذیر و snapshot تعداد/سطح کاربران، grantهای قبلی، نقش‌های Superadmin/Support و وضعیت Trial/Gold تهیه و صحت بازیابی آن بررسی شود.
2. این branch روی یک دیتابیس staging جدا از production با `MARKET_ACCESS_V2_ENABLED=False` migrate شود؛ سپس `check`، migration drift و تست API با JWT واقعی اجرا شود.
3. دسترسی‌های Level 1، Basic، Pro، Gold، Trial، Superadmin و Support با مقادیر واقعی API و مجوزهای هر بازار بررسی شوند. درخواست Trial کمپینی فقط پس از preview و تأیید cohort آزمایشی انجام شود.
4. فرانت جدید باید فقط `market_access_v2` را برای Tier/Trial ملاک بگیرد؛ `access_level` قدیمی تا پایان cutover برای سازگاری باقی می‌ماند.
5. پس از تست rollback، روشن‌کردن پرچم در production به‌صورت مرحله‌ای بررسی شود. خاموش‌کردن پرچم، rollback سریع رفتار است؛ حذف migrationهای افزوده پس از ثبت دادهٔ V2 بدون برنامهٔ جداگانه مجاز نیست.

## بررسی مقصد پرترافیک بازار

IP `31.7.66.189` در فایل‌های فعلی مخزن، فایل‌های پنهان محلی یا تاریخچهٔ Git به‌صورت مستقیم پیدا نشد. میزبان‌های پیش‌فرض بازار در DNS محیط توسعه نیز اکنون به آن IP resolve نشدند. این بررسی جای مشاهدهٔ DNS/اتصالات و تنظیمات runtime سرور production را نمی‌گیرد؛ منبع دقیق اتصال HTTPS هنوز اثبات نشده است. هیچ قانون firewall یا محدودیت بیرونی تغییر نکرد. سقف دانلود جدید از خواندن پاسخ چندده‌مگابایتی در مسیرهای JSON بازار/نمودار جلوگیری می‌کند، اما به‌تنهایی ثابت نمی‌کند تمام ترافیک آن IP قطع شده است.

پس از استقرار کد روی محیط آزمایشی/سرور، دستور فقط‌خواندنی `python manage.py audit_outbound_ip 31.7.66.189` میزبان‌های تنظیمات خارجی، feedهای فعال خبر و base URL دستیار را با DNS همان سرور مقایسه می‌کند. خروجی فقط نام setting یا شناسهٔ feed و hostname را برای match چاپ می‌کند، نه URL کامل، query یا API key. خروجی بدون match نیز انتساب تاریخی را رد نمی‌کند و همهٔ اتصال‌های احتمالی خارج از این فهرست را پوشش نمی‌دهد. قبل از حذف provider یا غیرفعال‌کردن feed باید match و اثر آن بر API بررسی شود.
